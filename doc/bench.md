# 视频处理性能优化记录

本文依据同一视频各轮 `make bench` 的实测 summary 整理。最终吞吐从 **18.37 FPS 提高到 59.73 FPS（约 3.25 倍）**，处理耗时从 **286.22 秒降到 88.03 秒（减少约 69.2%）**。

## 测量条件

| 项目 | 配置 |
|---|---|
| 视频 | `data/video/test.mp4` |
| 分辨率 / 帧数 | 1920×1080 / 5258 帧 |
| 原始帧率 / 时长 | 20.0045 FPS / 约 262.84 秒 |
| 检测模型 / 输入尺寸 | YOLO26m / 640×640 |
| 姿态模型 / 输入尺寸 | RTMW-X / 192×256 |
| 推理配置 | TensorRT FP16，device_id=0，workspace_mb=1024 |
| 关键点绘制阈值 | 0.6 |
| 输出编码 | OpenCV VideoWriter，mp4v，保持原视频帧率 |
| 系统 | Windows 10，16 个逻辑 CPU |
| 软件环境 | Python 3.12.13、NumPy 2.5.3、OpenCV 4.14.0、ONNX Runtime GPU 1.22.0、rtmlib 0.0.16 |
| OpenCV 线程数 | 16（后续报告记录值） |

整体 FPS = 完成帧数 / 视频处理墙钟时间，包含解码、推理、绘制、编码、统计写入和编码收尾，不包含模型初始化。所有帧均处理，不主动跳帧；模型初始化在各轮约为 7.88～13.56 秒，独立记录。

CPU/GPU 型号、GPU 频率、功耗、温度及后台负载未完整记录。各轮为单次测量，未做重复试验与误差区间统计；小幅变化不能直接归因于某一项改动。

## 各轮整体表现

轮次名称用于本文对照，V2～V5 对应 summary 的 `schema_version`。最初的串行版本和单人流水线版本没有 schema_version。

| 轮次 | 改动 | FPS | 总耗时（秒） | 相对实时速度 | 相对上一轮 FPS |
|---|---|---:|---:|---:|---:|
| A：串行基线 | 逐帧解码 → 多人姿态 → 绘制 → 编码 | 18.37 | 286.22 | 0.918× | — |
| B：单人流水线 | 最大人体姿态；解码、推理、绘制编码三阶段并行 | 35.64 | 147.53 | 1.782× | +94.0% |
| V2：细分统计 | 拆分检测预处理、推理调用、后处理 | 35.70 | 147.30 | 1.784× | +0.2% |
| V3：预处理前移 | 输入线程完成检测图像预处理；原地归一化 | 44.46 | 118.26 | 2.223× | +24.6% |
| V4：调用内计时 | 拆分布局复制、session.run、输入释放等 | 45.04 | 116.75 | 2.251× | +1.3% |
| V5：直接构造 NCHW | 输入线程直接生成最终张量，移除推理线程布局复制 | **59.73** | **88.03** | **2.986×** | **+32.6%** |

B 同时改变了目标数量与执行调度，无法从这组数据独立量化“单人选择”和“流水线并行”的贡献。V2、V4 主要用于增加观测信息，其小幅 FPS 变化不应当作确定的优化收益。

## 各模块平均耗时

单位为毫秒/帧。`—` 表示当时没有独立计时，不能当作零。姿态估计平均值包含无人帧的零耗时；最终版本 5258 帧中有 5255 帧执行姿态估计。

| 模块 | A：串行 | B：单人流水线 | V2 | V3 | V4 | V5 |
|---|---:|---:|---:|---:|---:|---:|
| 视频解码 | 6.228 | 9.373 | 9.072 | 9.604 | 9.514 | **8.256** |
| 人体检测（完整服务时间） | — | 22.069 | 21.860 | 20.898 | 20.656 | **14.430** |
| 单人姿态估计 | — | 5.945 | 6.114 | 5.844 | 5.725 | **6.448** |
| 骨架绘制 | — | 1.713 | 1.717 | 1.830 | 1.846 | **2.161** |
| 检测＋姿态＋绘制 | 34.616 | 29.727 | 29.691 | 28.572 | 28.227 | **23.040** |
| 视频编码写入 | 13.526 | 14.265 | 14.131 | 14.873 | 14.472 | **12.665** |

串行基线每帧约 54.44 ms，解码和编码合计约 19.75 ms，占约 36.3%。流水线通过重叠这些工作提升吞吐，并不要求每一个模块的耗时都下降。并发调度与资源竞争可能使某些模块的墙钟耗时增加。

V3 起，完整检测时间跨越输入线程和推理线程，仍包含检测预处理。**不能将“完整检测＋姿态”视为推理线程耗时，也不能将并行阶段耗时相加后取倒数作为整体 FPS。**

### 检测内部耗时

| 检测模块（ms/帧） | V2 | V3 | V4 | V5 |
|---|---:|---:|---:|---:|
| 图像预处理 | 9.504 | 4.657 | 4.577 | **4.536** |
| 推理调用（父项） | 11.565 | 16.103 | 15.946 | **9.729** |
| └ 输入布局整理 | — | — | 5.554 | **0.000** |
| └ feed 构造 | — | — | 0.041 | 0.009 |
| └ session.run | — | — | 9.918 | **9.710** |
| └ 输入引用清理 | — | — | 0.426 | 0.002 |
| └ 输出数组提取 | — | — | 0.003 | 0.003 |
| └ 调用内未归类开销 | — | — | 0.004 | 0.005 |
| 检测后处理 | 0.118 | 0.129 | 0.124 | 0.155 |
| 检测外层未归类开销 | — | 0.009 | 0.010 | 0.009 |

带 `└` 的项目属于推理调用子项，不要与父项重复相加。`session.run` 是同步调用墙钟时间，包含运行时执行、传输及同步，不是纯 GPU 内核时间。

V2 的三个检测子项未覆盖约 0.67 ms 外层开销。后续补充了计时，且预处理统计包含函数返回时的局部数组清理，因此不能将这些细项变化全部归因于计算加速。

V3 虽已把缩放、补边、颜色转换、浮点转换和归一化移到输入线程，仍在推理线程执行 HWC → 连续 NCHW 的布局复制。V4 确认这一步平均需要 **5.554 ms**。

V5 直接向最终连续 NCHW float32 张量写入 RGB 通道的归一化结果，避免 HWC 浮点中间数组及后续布局复制。`detection_input_layout=0` 表示推理线程不再做布局转换；张量生成成本计入输入阶段预处理，不是凭空消失。

V4 → V5 的关键证据：

- 图像预处理维持在约 4.5 ms，包含最终张量生成后没有明显增加。
- 检测 session.run 维持在约 9.7～9.9 ms，运行时调用本身变化不大。
- 检测推理调用减少约 6.217 ms，推理线程总耗时减少约 5.465 ms。
- 姿态估计增加约 0.723 ms，抵消了部分收益；原因尚未通过进一步 profiling 确认。

## 流水线阶段与瓶颈转移

最终结构：

```text
输入线程：解码 → 检测预处理 → 最终 NCHW 张量
                       ↓ 有界队列（容量 2）
推理线程：检测运行时调用 → 选最大人体 → 单人姿态估计
                       ↓ 有界队列（容量 2）
输出线程：骨架绘制 → 视频编码 → 逐帧统计
```

| 阶段平均耗时（ms/帧） | V2 | V3 | V4 | V5 |
|---|---:|---:|---:|---:|
| 输入阶段 | 9.072 | 14.261 | 14.090 | **12.792** |
| 推理阶段 | 27.979 | 22.455 | 22.170 | **16.705** |
| 输出阶段 | 15.853 | 16.709 | 16.324 | **14.833** |
| 实际 FPS | 35.70 | 44.46 | 45.04 | **59.73** |

V2 输入阶段仅解码；V3 起包括检测预处理，V5 进一步包含最终张量布局生成。输出服务时间包含首帧编码器初始化，不包含统计写入和编码器最终收尾；这些开销仍计入整体处理时间。

最终各阶段的估算能力与工作占比：

| 阶段 | 平均服务时间 | 估算处理能力 | 服务时间 / 总墙钟时间 |
|---|---:|---:|---:|
| 输入 | 12.792 ms | 78.18 FPS | 76.40% |
| 推理 | 16.705 ms | **59.86 FPS** | **99.78%** |
| 输出 | 14.833 ms | 67.42 FPS | 88.59% |

估算处理能力为平均服务时间的倒数，不是独立实测吞吐。实际 59.73 FPS 与推理阶段 59.86 FPS 接近，表明当前仍主要受推理阶段限制。输出阶段也已接近瓶颈：若其耗时不变，继续加速推理后可能在约 67 FPS 附近受输出限制。

上述工作占比不是 CPU 使用率，也不是 GPU 利用率。用户早期观察到 CUDA 利用率约 35%～36%，但各轮没有同步记录 GPU 遥测，不能据此给出优化后的利用率变化。

## 排队与单帧延迟

| 指标（ms） | A：串行 | B：单人流水线 | V2 | V3 | V4 | V5 |
|---|---:|---:|---:|---:|---:|---:|
| 单帧延迟 P50 | 55.67 | 124.11 | 122.85 | 103.17 | 102.33 | **80.03** |
| 单帧延迟 P95 | 71.36 | 155.15 | 158.98 | 130.98 | 121.31 | **93.28** |
| 单帧延迟 P99 | 82.47 | 184.22 | 173.70 | 152.32 | 138.15 | **107.06** |
| 推理前平均等待 | — | — | 74.65 | 52.99 | 52.32 | **37.14** |
| 输出前平均等待 | — | — | 0.15 | 0.24 | 0.08 | **0.38** |

单帧延迟从解码开始计到编码调用返回，不包含最后的编码器收尾。串行版本没有流水线排队；并行版本包含队列等待和背压，所以吞吐提高的同时，延迟可以高于串行版本。

V3 起推理前等待从输入准备结束算起，不包含已移到输入线程的检测预处理。增大队列主要增加缓存和延迟，不会消除当前推理瓶颈。

## 识别结果与精度边界

性能优化期间未降低检测/姿态输入分辨率，未换成更小模型，未主动跳帧。归一化与张量布局优化的目标是保持原有输入语义。但 A → B 将多人姿态改成最大人体单人姿态，识别范围发生变化；不能将 3.25 倍吞吐全部理解为相同多人任务的等价加速。

`make verify` 已比较原生 rtmlib balanced（YOLOX-M＋RTMW-X，ORT CUDA）与当前实现（YOLO26m＋RTMW-X，TensorRT FP16），双方各自选择最大人体。提供的验证结果覆盖 **200 帧**，不是性能测试的完整 5258 帧。

| 验证指标 | 实测结果 |
|---|---:|
| 双方均检测到人体 | 199/200 帧 |
| 仅基线检测到 | 1 帧 |
| 最大框 IoU ≥ 0.5 | 196/199 个双方有检测帧 |
| 平均框 IoU | 0.751 |
| 匹配框内双方高置信度关键点数 | 19,530 |
| 上述点平均 / P50 / P95 距离 | 5.46 / 3.32 / 15.28 px |
| 上述点距离 ≤ 5 px 比例 | 68.20% |
| 上述点距离 ≤ 基线框对角线 5% 比例 | 97.99% |
| 置信度跨越 0.6 阈值的分歧 | 1,930/26,467 个双方有检测帧的关键点，约 7.29% |

这是方案间一致性比较，不是标注数据上的准确率、召回率或优化等价性证明。检测模型和执行后端同时不同，框差异也会改变姿态裁剪。若需要确认优化是否影响精度，应使用同一模型和后端比较旧、新预处理，并固定同一人体框比较 CUDA 与 TensorRT 姿态输出。

## 运行与结果文件

```bash
make bench
make verify
```

性能测试输出到 `data/output/<video_name>/`：

- `pose.mp4`：单人骨架叠加视频。
- `frame.csv`：逐帧耗时。
- `summary.json`：整体及模块性能统计。

一致性验证输出到 `data/output/<video_name>/verify/`：

- `summary.json`：检测与关键点差异汇总。
- `frame.csv`：逐帧差异。
- `prediction.jsonl`：两套方案的原始框、关键点与置信度。

重复运行会覆盖对应输出；需要跨版本对比时，先保留旧报告。运行日志按 UTC+08:00 日期写入 `log/log_YYYY-MM-DD.log`。

## 后续优化重点

1. 拆分当前约 6.45 ms 的姿态估计，确认预处理、输入整理、运行时和后处理占比。
2. 同时评估约 12.67 ms 的视频编码，避免推理优化后迅速转为输出瓶颈。
3. 若需要优化检测运行时，采集算子分配和 GPU 时间线，区分执行、传输与同步；不能把 9.71 ms 的 session.run 全部当作 GPU 计算。
4. 对候选改动重复运行，记录 GPU 型号、频率、温度及系统负载，并用一致性验证检查输出变化。
